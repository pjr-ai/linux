## 一、基本概念

| 概念 | 含义 |
|---|---|
| 客户端 | 发起请求的一方（浏览器、App） |
| 服务器 | 提供服务、数据、资源的机器 |
| 请求 Request | 客户端向服务器要数据 |
| 响应 Response | 服务器返回给客户端的数据 |
| URL | 统一资源定位符，网络上每个资源的唯一地址 |

**一句话记忆**：请求是"我要"，响应是"它给"。

## 二、IP 地址

- IP = 网络上每台机器的"门牌号"，**全球唯一**
- 本质是 32 位二进制数，日常用十进制表示，以 `.` 分隔（如 `192.168.1.1`）
- 分为两部分：**网络号** + **主机号**

### 公网IP vs 内网IP

| 类型 | 说明 |
|---|---|
| 内网IP（私网） | 局域网内部使用，如 `192.168.x.x`、`10.x.x.x`、`172.16~31.x.x` |
| 公网IP | 真正在互联网上能被访问到的地址 |

**为什么我家路由器上的IP和百度查到的IP不一样？**
因为路由器做了 NAT（地址转换），你内网用私网IP，出口时被换成公网IP。这也是为什么虚拟机里的 CentOS 是 `192.168.x.x` 却也能上网。

## 三、子网掩码

**作用只有一个**：把 IP 地址划分成"网络号"和"主机号"两部分。

例：IP `192.168.1.1`，子网掩码 `255.255.255.0`
- 掩码里 24 个 "1" → IP 前 24 位是网络号
- 掩码里 8 个 "0" → IP 后 8 位是主机号

### 常用掩码

| 子网掩码 | 可用主机数 |
|---|---|
| 255.255.255.0 | 256 - 2 = **254 个**（首尾不能用：全0是网络地址，全1是广播地址）|
| 255.255.0.0 | 约 65023 个 |

**运维要求**：知道它是干嘛的就行，**不用会算子网划分**（那是网络工程师的活）。

## 四、网关

- 网关 = 你的网络**通向其他网络的出口**
- 一般是路由器，你家 WiFi 的网关通常就是路由器地址（如 `192.168.1.1`）
- **没有网关，你只能和同一局域网内的设备通信，出不了"门"**

查看网关命令：
```bash
ip route            # default via x.x.x.x 后面那个就是网关
```

## 五、DNS

- DNS = 把**域名翻译成 IP** 的"电话簿"
- 你记不住 `110.242.68.66`，但记得住 `baidu.com`
- 流程：输入域名 → 问 DNS 服务器 → 拿到真实 IP → 才能访问

### 实用技巧
- **改 hosts 文件可以绕过DNS**：`/etc/hosts` 里写 `IP 域名`，本机优先走这里（以后做测试环境常用）
- **面试常问**：DNS 用的是 **UDP 53 端口**（区域传送用TCP 53）

```bash
nslookup baidu.com      # 查域名解析
cat /etc/resolv.conf    # 看本机用的DNS服务器
```

## 六、DHCP

**DHCP = 自动给你的设备分配 IP 地址的服务**（你家路由器就在干这个活）。

### 对比

| 方式 | 说明 | 谁用 |
|---|---|---|
| DHCP 动态分配 | 自动获取IP，可能变化 | 家庭电脑、手机、测试虚拟机 |
| 静态 IP | 手动写死，固定不变 | **服务器必须用静态IP**（IP一变服务就连不上） |

### DORA 四步（面试点，和三次握手并列）

| 步骤 | 方向 | 内容 |
|---|---|---|
| **D**iscover | 客户端 → 服务器 | "谁给我个IP？" |
| **O**ffer | 服务器 → 客户端 | "这个IP给你行不行？" |
| **R**equest | 客户端 → 服务器 | "我要了" |
| **A**ck | 服务器 → 客户端 | "成交，给你了" |

端口：服务器 **UDP 67**，客户端 **UDP 68**

查看本机是DHCP还是静态：
```bash
cat /etc/sysconfig/network-scripts/ifcfg-ens33
# BOOTPROTO=dhcp   → DHCP自动获取
# BOOTPROTO=static → 静态IP
```

| 443 | HTTPS |
| 3306 | MySQL |
| 6379 | Redis |
| 53 | DNS |

| 25 | SMTP（邮件）|

### 端口范围
- 0-1023 知名端口（需要root才能监听）
- 1024-65535 动态/自定义端口

```bash

```

## 八、TCP vs UDP

| | TCP | UDP |
|---|---|---|
| 特点 | 可靠、有序、先建连接 | 快、不可靠、直接发 |
| 类比 | 打电话（先说好再聊）| 发短信（发出去不管）|
| 场景 | 网页、SSH、MySQL | DNS、视频直播、游戏 |

**运维打交道最多的服务（HTTP、SSH、MySQL）几乎全是 TCP。**

## 九、三次握手 / 四次挥手

### 四个标志位
| 标志 | 含义 |
|---|---|
| SYN | 请求建立连接 |
| ACK | 确认收到 |
| FIN | 请求断开连接 |
| RST | 强制重置（异常断开）|

### 三次握手（建立连接）
```
客户端                                服务器
  │ ──── SYN=1, seq=x ────────────→ │    "我要连你"
  │ ←─── SYN=1, ACK=1, seq=y,ack=x+1│    "行，我也准备好了"
  │ ──── ACK=1, ack=y+1 ──────────→ │    "成交，开始传数据"
```

**为什么是三次？**
让双方都各自确认两件事："我能发到你这""你能发到我这"。两次不够（服务器不知道客户端是否收到），四次多余。

### 四次挥手（断开连接）
双方各自说一次"我不发了"，对方回一次"收到"，共四次。
（因为TCP是全双工，两个方向要各自关闭）

## 十、TCP 连接状态 ⭐运维重点

```bash
ss -ant                # 查看所有TCP连接及状态
ss -ant | grep ESTAB   # 只看已建立的
ss -ant | grep -c TIME_WAIT   # 统计TIME_WAIT数量
```

| 状态 | 含义 | 运维关注点 |
|---|---|---|
| **LISTEN** | 服务在监听端口 | **服务没起来 → 没有这个状态，第一排查点** |
| **ESTABLISHED** | 连接已建立，正常通信 | 数量暴涨可能有异常/攻击 |
| **TIME_WAIT** | 主动关闭方保留约2分钟 | 大量出现（压测、频繁重启）会占端口 |
| **CLOSE_WAIT** | 对方已关，本方程序还没关 | **大量 CLOSE_WAIT = 程序有bug没释放连接** |
| SYN_RECV | 收到SYN但未完成握手 | 大量出现可能是 **SYN Flood 攻击** |

### 高频面试题：服务器上大量 CLOSE_WAIT 怎么办？
> 说明**应用程序没有正确关闭连接**（代码问题，不是系统问题）。
> 排查思路：统计数量和对方IP → 定位是哪个服务 → 检查代码里连接是否正常关闭（try-finally / 连接池配置）。

## 十一、HTTP 协议

**HTTP = 超文本传输协议**，浏览器和服务器之间"说话的规矩"。

### 核心特点

#### 1. 请求-响应模型
永远是**客户端主动问，服务器被动答**。服务器不会主动推送（除非WebSocket）。

#### 2. 无状态 ⭐
**"无状态" = 服务器不记得你上一次是谁。**
你登录了，下一次请求服务器理论上又不认识你了。

**怎么解决登录保持？**
- **Cookie**：登录成功后服务器发给你一张凭证（存浏览器里），之后每次请求自动带上
- **Session**：服务器端保存会话信息，靠Cookie里的 sessionid 对应
- **Token**（如JWT）：放在请求头 `Authorization` 里

> **面试题**：HTTP是无状态的，怎么保持登录状态？ → 答：Cookie + Session，或请求头携带Token。

#### 3. 无连接 → 长连接
- HTTP/1.0：每个请求新建一个TCP连接，用完就断
- HTTP/1.1：默认**长连接（Keep-Alive）**，一个连接发多个请求
- **这就是为什么会有 TIME_WAIT、会有"连接数"概念**

### 请求报文结构（四部分）
```
POST /api/login HTTP/1.1            ← ① 请求行：方法 + 路径 + 版本
Host: www.example.com               ← ② 请求头
User-Agent: Mozilla/5.0
Content-Type: application/json
Content-Length: 45
Cookie: sessionid=abc123
Authorization: Bearer xxxxx
Referer: https://example.com
                                    ← ③ 空行
{"username":"tom","pwd":"123"}      ← ④ 请求体
```

### 常见请求头

| 头 | 作用 |
|---|---|
| Host | 访问的是哪个网站（虚拟主机靠它区分） |
| User-Agent | 客户端类型（浏览器/爬虫） |
| Content-Type | body 的数据格式（json/form） |
| Cookie | 身份凭证 |
| Referer | 从哪个页面跳来的 |
| Authorization | 认证信息（Token） |

### 响应报文结构（四部分）
```
HTTP/1.1 200 OK                     ← ① 状态行
Server: nginx/1.20.1                ← ② 响应头
Content-Type: text/html
Content-Length: 1024
Set-Cookie: sessionid=xyz
Cache-Control: max-age=3600
Last-Modified: Thu, 13 Sep ...
                                    ← ③ 空行
<html>...</html>                    ← ④ 响应体
```

### ⭐ 两个运维强相关的响应头
- **`Server: nginx/1.20.1`** → 服务器"自报家门"。安全加固的一条就是**隐藏 Server 头**，别暴露版本
- **`Set-Cookie`** → 服务器下发凭证用的
- **`Cache-Control` / `Last-Modified`** → 缓存相关，对应 304

### HTTP 方法

| 方法 | 作用 | 请求体 | 幂等 |
|---|---|---|---|
| GET | 查询 | 无 | ✅ |
| POST | 新增/提交 | 有 | ❌ |
| PUT | 全量更新 | 有 | ✅ |
| PATCH | 局部更新 | 有 | ❌ |
| DELETE | 删除 | 一般无 | ✅ |
| **HEAD** | 只要响应头 | 无 | ✅ |
| OPTIONS | 询问支持的方法 | 无 | ✅ |

**幂等**：同一操作执行一次和多次，结果一样。GET/PUT/DELETE 幂等，POST 不幂等（点两次下单就是两单）。

> **`curl -I` 用的就是 HEAD 方法**，所以只返回响应头。

### HTTP 版本演进

| 版本 | 特点 |
|---|---|
| 1.0 | 每个请求一个连接，慢 |
| **1.1** | 长连接 + Host头，**目前最主流** |
| 2 | 多路复用、头部压缩、二进制传输 |
| 3 | 基于 UDP（QUIC），更快抗丢包 |

## 十二、HTTP 状态码 ⭐

| 分类 | 含义 |
|---|---|
| 1xx | 信息（基本见不到） |
| 2xx | 成功 |
| 3xx | 重定向 |
| 4xx | 客户端错误 |
| 5xx | **服务器错误（运维的战场）** |

### 常用状态码

| 码 | 含义 | 说明 |
|---|---|---|
| 200 | OK | 成功 |
| 204 | No Content | 成功但无返回内容 |
| **301** | 永久重定向 | 地址永久搬家（http→https、加www）|
| **302** | 临时重定向 | 暂时跳转（登录后跳首页）|
| 304 | Not Modified | 内容没变，用浏览器缓存 |
| 400 | Bad Request | 请求格式错误 |
| **401** | Unauthorized | **没登录/认证失败** |
| **403** | Forbidden | **登录了但没权限** |
| **404** | Not Found | 页面/资源不存在 |
| **500** | Internal Server Error | **程序自己崩了** |
| **502** | Bad Gateway | **Nginx 连不上后端服务（后端挂了）** |
| **503** | Service Unavailable | 服务过载/维护中 |
| **504** | Gateway Timeout | **后端响应超时太慢** |

### ⭐ 401 vs 403
- **401 = 你是谁我不知道**（没登录）
- **403 = 我知道你是谁，但你不准进**（没权限）

### ⭐ 502 / 503 / 504（运维面试老面孔）
- **502**：Nginx 正常运行，但它后面的后端服务没起来/挂了
- **503**：服务在，但扛不住（过载）或在维护
- **504**：后端响应太慢，超时了

### 排查思路口诀
- **4开头** → 用户/权限问题，先看请求
- **5开头** → 服务端问题，**该你上了**

## 十三、HTTPS

**HTTPS = HTTP + 加密（TLS/SSL）**

多了 TLS 握手过程：协商加密算法、服务器出示证书、验证、生成会话密钥。
之后所有通信内容都是**加密**的。

**运维必记一点：证书会过期！**
大量真实故障（"网站凌晨突然打不开"）就是 SSL 证书到期。
→ 巡检项之一：**提前查证书到期时间**。

```bash
curl -vI https://baidu.com       # 可以看到TLS握手过程
```

## 十四、常用网络排查命令 ⭐

```bash
# 1. 查看本机IP和网卡
ip addr

# 2. 查看网关
ip route

# 3. 测试连通性（Ctrl+C 停止）
ping baidu.com

# 4. 看域名解析
nslookup baidu.com
dig baidu.com

# 5. 查看监听端口
ss -tlnp        # t=TCP l=listen n=数字 p=进程
ss -ant         # 所有TCP连接及状态

# 6. 测端口通不通
telnet 192.168.1.10 3306
curl -v telnet://192.168.1.10:3306

# 7. 看HTTP响应头
curl -I baidu.com      # 只发HEAD请求，不跟随跳转
curl -IL baidu.com     # -L 跟随跳转，能看到最终状态码
curl -v baidu.com      # -v 详细模式，打印完整请求头/响应头

# 8. 路由追踪
traceroute baidu.com
```

### `-I` 和 `-L` 的区别（今天亲手踩的坑）
- `curl -I baidu.com/abc123` → 返回 **301**（因为百度把你从 http 跳到 https+www）
- `curl -IL baidu.com/abc123` → 跟随跳转后，返回最终状态码 **404**

**结论：`-I` 只看第一站响应头，`-L` 才跟到底；排查要看最终状态码。**

## 十五、面试题汇总

### Q1：三次握手是什么？
> 客户端发 SYN 请求建立连接，服务器回 SYN+ACK 确认，客户端再回 ACK 确认，三次之后连接建立，开始传数据。目的是让双方都确认"自己发的能到、对方的能到"。

### Q2：⭐ 从输入网址到页面显示，发生了什么？
1. **DNS 解析**：域名 → IP
2. **TCP 三次握手**：和服务器建立连接（443端口）
3. **TLS 握手**（HTTPS）：验证证书、协商密钥
4. **发送 HTTP 请求**：GET /，带请求头
5. **服务器处理并响应**：返回状态码 200 + 页面内容
6. **浏览器渲染**：显示页面
7. **四次挥手**断开（HTTP/1.1 可能保持连接复用）

### Q3：401 和 403 的区别？
> 401 是没登录/认证失败；403 是已登录但无权限。

### Q4：服务器大量 CLOSE_WAIT 怎么办？
> 应用层没正确关闭连接，检查代码是否释放连接；统计数量与来源IP定位服务。

### Q5：500、502、503、504 分别什么含义？
> 500 程序内部错误；502 网关连不上后端；503 服务不可用（过载/维护）；504 后端响应超时。

### Q6：HTTP 是无状态的，怎么保持登录？
> Cookie + Session，或请求头携带 Token。

### Q7：DHCP 的四步？
> Discover → Offer → Request → Ack（DORA）。

### Q8：服务器为什么用静态IP？
> IP 固定不变，服务/配置不会因为IP变化而失联；DHCP 动态IP可能变动。
