ip 网络层给每台主机分配的逻辑地址
掩码 标明ip哪部分是网络号、哪部分是主机号
网关 本网段的出口（如 192.168.1.1），目标不在本网段时数据包交给它转发。
DNS  把域名翻译成 IP 的服务（如 114.114.114.114），它挂了就是"能 ping 通 IP、打不开域名"。
端口 同一IP 上区分不同服务的编号（22 SSH / 80 HTTP / 443 HTTPS），TCP 建连要 IP + 端口都对。

#排查思路
网络排查的原则是从下往上、逐层排除，每一步都缩小范围。先用 ping 确认三层可达，不通就先 ping 网关把"本机问题"和"外部问题"切开；网关通、公网 IP 通而域名不通，问题就锁定在 DNS，去看 /etc/resolv.conf 并换服务器验证。网络和 DNS 都没问题，再用 traceroute/mtr 定位路径上哪一跳开始丢包，注意中间 * 不等于故障。最后用 curl -v 打到应用层，确认 TCP 是否连上、返回什么状态码，并用 -w 拆出 DNS、建连、TLS、总耗时，判断慢在哪一环、责任方是谁。整套动作的价值在于：每次都先问"这一层通了没有"，通了就往上走一层，不通就在这一层找原因，而不是凭感觉重启网卡。理清"IP/掩码决定同网段还是走网关、DNS 决定名字能否变成 IP、端口决定服务能否连上"这条链，故障就能被稳稳框在某一层里。查资料
#从敲网址到页面出现，中间发生了什么
URL 补全 → 查本地缓存（可能到这就结束了）→ 名字解析成 IP（本地 DNS 替你跑完整条迭代链）→ 内核按掩码决定直发还是交网关（ARP 拿 MAC）→ TCP 三次握手对上入口（CDN / LB，不是你以为的那台机器）→ HTTPS 再握手一次（SNI 报域名、验证书）→ 发 HTTP 请求穿到后端 → 返回状态码和数据（回程还过一遍缓存）→ 浏览器解析渲染上屏。查资料




ping 网关 → 通不通本机到出口；ping 公网 IP → 分界"网络 vs DNS"。
nslookup 域名 → 看 Server（DNS 是谁）和 Address（解析结果）；不通先查 /etc/resolv.conf。
traceroute -n -w 1 -q 1 → 看第几跳开始丢/慢；中途 * 不代表坏，看是否延续到目标。
curl -v -I → Connected 看 TCP 通、200 看服务正常、>/< 看请求响应头。
curl -w 拆 DNS/CONNECT/TLS/TOTAL → DNS 慢是解析、CONNECT 慢是网络、TOTAL 慢是服务端。
